# 사내 일정 관리 툴 — 제품 방향 및 구현 기준

> 최종 갱신: 2026-08-21  
> 이 문서는 이후 화면·데이터·권한 구현의 기준입니다.

## 제품 방향

이 툴은 구글 시트의 데이터를 읽어 보여주는 대시보드가 아니라, **사내 일정과 업무를 직접 생성·배정·관리하는 단일 원장**이다.

- 모든 업무·일정·프로젝트 정보는 이 툴에서 관리한다.
- 변경은 Firebase Firestore에 저장하고, 접속 중인 모든 사용자의 화면에 실시간으로 반영한다.
- 구글 시트는 업무 입력 원본으로 사용하지 않는다. 필요할 경우 나중에 백업 또는 내보내기 용도로만 연동한다.
- 프로젝트 일정과 실무 일정은 화면상 구분하지만, 같은 프로젝트·업무 데이터를 함께 사용한다.

## 사용자와 권한

사용자는 Google 로그인으로 입장한다. 로그인한 계정의 Firebase UID(및 이메일)에 연결된 권한 정보를 조회해 역할을 자동 적용한다. 사용자가 역할이나 소속 부서를 직접 선택하지 않는다.

| 역할 | 범위 | 권한 |
|---|---|---|
| 관리자 (`admin`) | 전체 회사 | 사용자·권한·부서·프로젝트·마일스톤·모든 업무를 생성, 수정, 삭제한다. |
| 팀장 (`lead`) | 관리자가 지정한 한 부서 | 해당 부서의 모든 팀원과 업무를 관리하고, 업무를 생성·배정·수정·삭제한다. |
| 팀원 (`member`) | 본인에게 배정된 업무 | 배정된 업무를 조회하고, 본인 업무의 상태·진행률·일정·내용을 수정한다. 다른 사람의 업무와 프로젝트 기준 정보는 조회만 한다. |

- 팀장은 `role: lead`와 담당 `departmentId`를 함께 가진다.
- 팀원은 여러 프로젝트에 참여할 수 있지만, 수정 권한은 자신의 `assigneeId`가 설정된 업무에만 생긴다.
- 프로젝트명, 프로젝트 참여 부서, 공통 마일스톤은 팀원이 수정하지 않는다.
- 첫 관리자 계정은 배포 시 사전 등록한다. 새 사용자가 처음 로그인하면 본인 UID의 `accessRequests` 승인 요청만 만들고 `승인 대기` 상태로 둔다. 관리자가 이메일을 기준으로 `users/{uid}`에 역할과 부서를 할당한 뒤 접근을 허용한다.
- 사용자는 본인의 역할, 부서, 승인 상태를 직접 생성하거나 변경할 수 없다.
- 화면에서 버튼을 숨기는 것에 그치지 않고 Firestore 보안 규칙에서도 같은 권한을 강제한다.

```js
users/{uid} = {
  email: "designer@company.com",
  name: "홍길동",
  role: "member",       // admin | lead | member
  departmentId: "ui",
  active: true,          // false면 로그인 후 승인 대기 화면만 표시
  approvedAt: "server timestamp"
}
```

`accessRequests/{uid}`에는 신규 사용자의 이메일, 이름, 요청 시각만 저장한다. 이 요청에는 역할·부서·승인 상태 필드를 넣지 않으며, 관리자만 `users/{uid}` 권한 문서를 생성하거나 변경한다.

## 로그인 후 화면 구조

로그인 후 상단의 큰 메뉴는 두 개다.

```text
로그인
  └─ 메인
      ├─ 프로젝트 일정
      └─ 실무 일정
```

### 프로젝트 일정

프로젝트를 기준으로 전체 진행 상황을 확인하는 공간이다.

- 전체 프로젝트 현황: 프로젝트 카드, 전체 진행률, 완료/전체 업무 수, 다음 마감일, 지연 여부
- 부서별 현황: 기획·UI·개발 등 참여 부서의 진행률과 업무 수
- 프로젝트 상세: PC/모바일 구분, 공통 마일스톤, 부서별 업무, 담당자, 상태, 일정, 선행 업무를 한 흐름으로 표시
- 팀원은 자신에게 배정된 프로젝트를 본다. 해당 프로젝트 안에서는 전체 부서의 업무 흐름을 조회할 수 있지만, 수정은 본인에게 배정된 업무로 제한한다. 팀장과 관리자는 전체 프로젝트를 본다.
- 관리자만 프로젝트와 공통 마일스톤을 생성·관리한다. 팀장은 자기 부서 업무를 프로젝트에 추가·관리할 수 있다.

### 실무 일정

사람과 부서를 기준으로 실제 업무를 생성·배정·처리하는 공간이다.

- 팀원: 내 업무 목록, 내 캘린더, 상태·진행률·일정 업데이트
- 팀장: 담당 부서의 팀원별 업무, 팀 캘린더, 업무 생성과 담당자 배정, 업무량 확인
- 관리자: 부서를 선택해 전체 팀의 실무 일정을 관리
- 업무는 프로젝트에 연결할 수 있으며, 연결된 업무의 상태와 일정은 프로젝트 일정에도 즉시 반영된다.
- 프로젝트와 무관한 팀 내부 업무도 등록할 수 있다.

## 핵심 데이터 관계

```text
부서 ── 사용자
          └─ 역할(admin / lead / member)

프로젝트
 ├─ 버전(PC / 모바일, 선택)
 ├─ 마일스톤
 └─ 업무
     ├─ 담당 부서
     ├─ 담당자(초기 버전은 1명)
     ├─ 상태 / 진행률
     ├─ 시작일 / 마감일
     └─ 선행 업무(선택)
```

업무는 한 번만 저장한다. 같은 업무가 `실무 일정`에는 담당자·부서 관점으로, `프로젝트 일정`에는 프로젝트 관점으로 표시된다.

```js
tasks/{taskId} = {
  projectId: "pc12",          // 프로젝트 외 업무면 null
  version: "pc",              // pc | mobile | null
  milestoneId: "milestone-id", // 선택: 프로젝트 안의 마일스톤
  departmentId: "ui",
  assigneeId: "firebase-uid",
  title: "캐릭터 선택 화면 시안",
  status: "in_progress",     // todo | in_progress | done | blocked
  progress: 50,               // todo=0, done=100, in_progress=1~99
  estimatedDays: 2.5,         // 예상 작업일. 업무량 계산에 사용
  startDate: "2026-08-24",
  dueDate: "2026-08-28",
  dependsOn: ["task-id"],
  archivedAt: null,           // 삭제 대신 보관, null이면 활성 업무
  createdBy: "firebase-uid",
  updatedAt: "server timestamp",
  updatedBy: "firebase-uid"
}
```

### 업무 상태와 보관 규칙

- `todo`는 진행률 `0`, `in_progress`는 `1~99`, `done`은 `100`으로 일관되게 저장한다.
- `blocked`는 현재 진행률을 유지하되, 프로젝트 현황과 실무 일정에서 차단 상태를 명확히 표시한다.
- 초기 버전은 업무 하나에 담당자 한 명만 지정한다. 여러 명 협업은 후속 버전에서 참여자 기능으로 확장한다.
- 업무 삭제는 기본적으로 `archivedAt`을 기록하는 보관 처리다. 보관 업무는 일반 화면과 진행률 계산에서 제외하되, 이력과 선행 업무 참조는 유지한다.
- 영구 삭제는 선행 업무·변경 이력에 영향을 주므로 관리자만 수행할 수 있으며, 기본 운영 흐름에는 넣지 않는다.

## 실시간 동기화와 변경 기록

- 프로젝트, 업무, 사용자 권한은 Firestore 컬렉션으로 저장한다.
- 프로젝트와 실무 화면은 필요한 문서를 실시간 구독(`onSnapshot`)한다.
- 누군가 업무를 수정하면 다른 사용자의 카드·목록·캘린더·진행률이 새로고침 없이 갱신된다.
- 초기 버전에서는 업무의 `createdBy`, `updatedAt`, `updatedBy`를 저장한다. 담당자·상태·마감일의 상세 변경 이력(`activityLogs`)은 신뢰성 있는 서버 측 처리(Cloud Functions 등)를 도입하는 2단계 기능으로 구현한다.
- 진행률은 연결된 업무 기준으로 계산한다. 수동으로 서로 다른 수치를 이중 입력하지 않는다.
- 프로젝트 진행률과 프로젝트 건강 상태는 구분한다. 진행률은 업무로 자동 계산하고, 팀장 또는 관리자는 `정상`·`주의`·`위험` 상태와 주간 업데이트(완료·막힌 일·다음 계획)를 작성한다.
- 업무에는 실시간 댓글과 참고 링크를 남길 수 있다. 댓글의 `@이름` 표기는 멘션 정보로 저장하며, 실제 푸시 알림은 서버 자동화 단계에서 연결한다.

## 기존 파일 및 전환 방침

현재 구현은 구글 시트 3개를 읽는 읽기 전용 대시보드다. 새 방향으로 구현할 때의 처리 방침은 다음과 같다.

| 파일 | 현재 상태 | 전환 방침 |
|---|---|---|
| `index.html` | 대시보드 앱 셸과 기존 Firebase 초기화 | Google 로그인 화면과 2개 상위 메뉴 구조로 변경 |
| `js/state.js` | `board/shared` 단일 문서 구독 | 사용자·프로젝트·업무 컬렉션 및 권한 상태 관리로 재구성 |
| `js/render.js` | 읽기 전용 3개 화면 | 프로젝트 일정·실무 일정 및 역할별 편집 UI로 재구성 |
| `js/main.js` | 초기 동기화 버튼 | 로그인 초기화와 데이터 구독 진입점으로 변경 |
| `firestore.rules` | 없음 | 역할별 읽기·수정 범위를 서버에서 강제하는 Firestore 보안 규칙 |
| `firebase.json` | 없음 | `firestore.rules` 배포 설정 |

## 구현 순서

1. Firebase Authentication(Google 로그인)과 사용자 권한 데이터 모델을 구성한다.
2. Firestore 보안 규칙으로 관리자·팀장·팀원의 접근 범위를 강제한다.
3. 프로젝트·마일스톤·업무 데이터 모델과 기본 CRUD를 구현한다.
4. `프로젝트 일정` 전체 현황 및 프로젝트 상세 화면을 구현한다.
5. `실무 일정`의 개인·부서 일정, 업무 배정, 캘린더를 구현한다.
6. 실시간 구독, 진행률 계산, 지연 표시를 연결한다.
7. 상세 변경 이력(`activityLogs`)을 서버 측 처리와 함께 추가한다.
8. 필요 시 기존 구글 시트 데이터를 최초 1회 가져오기 하거나, 내보내기 기능을 추가한다.

## 이번 전환에서 확정된 결정

- 구글 시트는 실시간 업무 원본이 아니다.
- 로그인은 계정 기반이며, 권한과 부서는 관리자가 사전에 할당한다.
- 신규 로그인 계정은 관리자 승인 전까지 승인 대기 상태로 둔다.
- 상위 메뉴는 `프로젝트 일정`과 `실무 일정` 두 개다.
- 프로젝트 일정은 프로젝트 중심, 실무 일정은 사람·부서 중심이다.
- 변경 내용은 Firestore를 통해 실시간으로 모두에게 동기화된다.
- 업무는 초기 버전에서 담당자 한 명을 가지며, 삭제 대신 보관 처리한다.
- 업무는 프로젝트 마일스톤에 연결할 수 있고, 선행 업무가 미완료이면 `선행 대기`로 표시한다. 순환 선행 관계는 저장할 수 없다.
- 실무 일정은 목록·월간 캘린더·주간 업무량 보기로 같은 업무 데이터를 표시한다. 예상 작업일을 업무 기간의 평일에 나누어 1일 초과 배정을 경고한다.
- 사용자는 휴가·병가·외근 등 부재 일정을 등록할 수 있다. 부재일은 캘린더와 주간 업무량에 표시되며, 해당 날짜의 예상 작업량에서는 제외한다.
- 실무 일정 상단에는 지연 업무와 3일 이내 마감 업무를 표시한다. 이메일·메신저 알림은 후속 서버 자동화 단계에서 추가한다.
