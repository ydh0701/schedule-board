# 개발 착수 전 보완 결정

> `화면UX_재점검.md`와 `업무흐름_기반_재설계.md`를 구현 가능한 규칙으로 보완한다.

## 1. 결론

다음 기능은 화면 구현보다 먼저 확정·구현한다.

1. 기존 엑셀 데이터 이관
2. 업무량·가용성 계산 단일 공식
3. 실제 상태와 일정 상태의 조합 규칙
4. 마일스톤·업무 선후행 연결 규칙
5. 역할 × 화면 × 행동 권한표

휴가·연차·병가는 기존 결정대로 이 도구 범위에서 제외한다. 가용성 결과에는 `등록된 업무 기준 추정치`임을 표시한다.

---

## 2. 엑셀 이관 화면과 절차

사용자가 기존 업무를 하나씩 재입력하지 않도록, 관리자/PM 전용 `데이터 이관` 화면을 별도로 둔다.

```text
파일 선택(.xlsx/.csv)
→ 시트·헤더 확인
→ 열 매핑
→ 미리보기 및 오류 검증
→ 이관 실행
→ 결과 보고서 저장
```

### 지원할 원본 구조

| 원본 | 주요 열 | 대상 데이터 |
|---|---|---|
| 전체 마일스톤 | 프로젝트, 분류, 협업 직군, 시작·종료일, 워킹데이 | 프로젝트, 마일스톤, 업무 |
| 기획 개인 업무표 | 프로젝트, 업무, 시작일, 마감일, 워킹데이, 진척률 | 기획 업무 |
| UI 마일스톤 | 플랫폼, 작업자, 빌드 버전, 시스템, 내용, 기간, 완료 | UI 업무 |

### 이관 전 검증

- 프로젝트 코드가 없으면 새 프로젝트 생성 후보로 표시
- 이름이 퇴사자와 일치하면 과거 담당자로 유지하되 새 배정 후보에는 넣지 않음
- 담당자를 찾지 못하면 `미배정`으로 이관
- 날짜 형식, 마감일이 시작일보다 이른 경우, 알 수 없는 직군은 오류 목록으로 분리
- 오류가 있는 행만 제외하고 나머지를 임의로 저장하지 않는다. 사용자가 확인 후 실행한다.

### 이관 결과

- 생성/갱신/제외 행 수
- 제외 사유와 원본 행 번호
- 이관 배치 ID와 실행 시각
- 되돌리기: 같은 배치로 생성된 레코드만 관리자/PM이 보관 처리

## 3. 가용성·업무량 단일 계산식

### 기본 단위

- 1인 1일 가용량 = `1.0 일`
- 주간 기본 가용량 = `5.0 일` (`weeklyCapacity`으로 개인별 조정 가능)
- 주말과 국가 공휴일은 `0 일`
- 휴가·연차·병가·개인 일정은 계산에 포함하지 않는다.

### 업무별 일일 부하

```text
업무의 일일 부하
= 예상 워킹데이 ÷ 업무 기간 내 실제 근무일 수 × 담당 지분

개인의 특정 날짜 부하
= 그 날짜에 겹치는 모든 미완료 업무의 일일 부하 합계
```

예: 5 워킹데이 업무가 근무일 5일 동안 진행되고 주 담당 지분이 100%면, 하루 `1.0일`이다.

### 공동 담당 규칙

- `assignees`에는 각 담당자의 `share`(지분)를 기록한다.
- 주 담당자만 있으면 `100%`.
- 공동 담당자를 추가하면 지분 합계는 반드시 `100%`.
- 기본 제안값: 2명은 `50% / 50%`, 3명은 `34% / 33% / 33%`.
- 지분을 입력하지 않은 공동 담당은 저장할 수 없다. 업무량을 임의로 100%씩 중복 계산하지 않는다.

### 판정 기준

| 상태 | 조건 | 배정 UI |
|---|---|---|
| 여유 | 기간 중 일일 부하가 0.8 이하, 주간 부하 80% 미만 | `배정할 수 있습니다` |
| 주의 | 일일 부하 0.8 초과 또는 주간 부하 80~100% | 경고 확인 후 저장 |
| 과부하 | 하루 부하 1.0 초과 또는 주간 부하 100% 초과 | `그래도 배정` 별도 확인 필요 |
| 계산 불가 | 시작일·마감일·워킹데이·지분 중 하나 없음 | 배정 전 보완 요구 |

`프로젝트 수`는 배지와 맥락 정보로만 사용하며, 별도 0.4/프로젝트 같은 가중치를 계산에 넣지 않는다. 실제 업무량과 중복되어 과대 평가될 위험이 있기 때문이다.

### 다음 가능일

오늘부터 순서대로 근무일을 검사해, 그날의 예상 부하가 `0.8 이하`가 되는 첫 날짜다. 화면에는 항상 `등록된 업무 기준 추정치`라는 보조 문구를 표시한다.

## 4. 실제 상태 × 일정 상태 규칙

### 필드 정의

| 구분 | 값 | 변경 주체 |
|---|---|---|
| 실제 상태 | 예정, 진행 중, 차단됨, 완료 | 업무 담당자/권한자 |
| 일정 상태 | 예정, 정상, 임박, 지연, 완료(정상), 완료(지연), 위험 | 시스템 계산 |

### 계산 우선순위

1. 실제 상태가 `완료`면 완료일과 마감일을 비교한다.
2. 실제 상태가 `차단됨`이면 날짜와 무관하게 일정 상태는 `위험`이다.
3. 시작일 전이면 `예정`.
4. 마감일이 지났고 미완료면 `지연`.
5. 남은 근무일이 3일 이하면 `임박`.
6. 그 외는 `정상`.

### 조합표

| 실제 상태 | 일정 상태 | 화면 표현 |
|---|---|---|
| 예정 | 예정 | 회색 `예정` |
| 진행 중 | 정상 / 임박 / 지연 | 실제 상태와 일정 상태를 각각 뱃지로 표시 |
| 차단됨 | 위험 | 빨강 `차단됨 · 일정 위험` |
| 완료 | 완료(정상) | 초록 `완료` |
| 완료 | 완료(지연) | 초록 완료 뱃지 + 보조 `마감 후 완료` |

완료 업무는 현재 시점에서 `지연`으로 계속 표시하지 않는다. 과거 이력으로만 완료 지연 여부를 보존한다.

## 5. 마일스톤·선후행 연결 규칙

### 마일스톤 연결 방식

업무 편집 패널에서 다음 둘 중 하나를 선택한다.

| 방식 | 저장 필드 | 날짜 변경 시 |
|---|---|---|
| 수동 일정 | `startDate`, `dueDate`, `scheduleMode: manual` | 자동 변경 없음 |
| 마일스톤 기준 일정 | `milestoneId`, `scheduleRule` | 기준 마일스톤 이동 시 미리보기 후 재계산 |

`scheduleRule`은 `마일스톤 날짜에서 마감까지의 근무일 오프셋`, `예상 워킹데이`를 가진다. 예: `데모 빌드 18근무일 전까지 완료`.

### 업무 간 선후행

- 업무는 복수의 선행 업무를 가질 수 있다.
- 기본 규칙은 `선행 완료 후 시작 가능`이다.
- 선행 업무가 지연되었다고 후행 업무를 자동으로 무조건 미루지 않는다.
- 대신 프로젝트 상세과 업무 편집 패널에서 `선행 지연 영향`을 경고하고, PM/팀장/담당자가 다음 중 하나를 선택한다.
  1. 후행 업무 일정 재계산
  2. 일정 유지(위험으로 기록)
  3. 선후행 연결 해제

자동으로 모든 일정을 밀면 수동 조율한 일정까지 훼손될 수 있으므로, 재계산은 항상 미리보기와 확인을 거친다.

## 6. 날짜·워킹데이 수정 규칙

기본 원칙은 `시작일 + 예상 워킹데이 → 마감일 자동 계산`이다.

마감일을 직접 바꾸면 다음 선택창을 보여 준다.

```text
마감일을 직접 변경했습니다.

(기본) 새 마감일에 맞춰 예상 워킹데이를 다시 계산
       → 시작일은 유지, 업무량도 새 워킹데이 기준으로 변경

마감일만 고정
       → 워킹데이는 유지, 일정은 수동 일정으로 전환
```

- 시작일을 변경하면 워킹데이는 유지하고 마감일을 다시 계산한다.
- 마일스톤 기준 일정은 날짜를 직접 수정할 때 `수동 일정으로 전환` 여부를 확인한다.
- 공휴일 변경도 같은 재계산 미리보기 규칙을 사용한다.

## 7. 모바일·작은 화면 규칙

| 화면 | 데스크톱 | 모바일 |
|---|---|---|
| 내 업무 | 행 목록과 열 정보 | 핵심 정보 2줄 + 행 확장 |
| 팀/인력 현황 | 테이블 | 사람 카드 + 상세 펼침 |
| 프로젝트 현황 | 가로 프로젝트 행 | 압축 프로젝트 카드 |
| 프로젝트 일정표 | 날짜 × 직군 그리드 | 주 단위 전환 + 직군 필터 + 세로 타임라인 |
| 업무 편집 | 오른쪽 패널 | 전체 화면 모달 |

프로젝트 상세의 데스크톱 그리드는 **왼쪽 날짜 / 위쪽 직군** 원칙을 유지한다. 동일 날짜·직군 업무가 많으면 `+N`을 표시하되, 모바일은 이 그리드를 그대로 축소하지 않고 선택 직군의 주간 타임라인을 기본으로 보여 준다.

| 내 업무 조회 | 본인 | 본인 | 본인 | 본인 |

| 팀 현황·인력 현황 | 불가 | 자기 팀 | 전체 | 전체 |

## 9. 실행 취소와 변경 이력

- 담당자 변경, 보관, 상태 변경 직후 10초 동안 화면 하단에 `되돌리기`를 표시한다.
- 되돌리기는 아직 다른 변경이 없는 경우에만 즉시 원복한다.
- 시간이 지나거나 다른 사람이 수정한 경우에는 변경 이력에서 이전 상태를 확인하고 새 변경으로 되돌린다.
- 모든 배정 변경은 이전/이후 담당자, 변경자, 시각, 과부하 경고 확인 여부를 기록한다.

## 10. 실시간 데이터와 비용 원칙

- `내 업무`, 현재 열려 있는 업무 편집 패널, 현재 열려 있는 프로젝트 상세만 실시간 구독한다.
- 프로젝트 현황·팀 현황·인력 현황은 화면 진입 시 읽고, 포커스 복귀·수동 새로고침·짧은 갱신 주기로 최신화한다.
- 장기적으로는 프로젝트별 집계 문서(진행률, 지연 수, 미배정 수, 직군 상태)를 별도로 저장해 대시보드가 전체 업무를 매번 읽지 않게 한다.
- 현재 정적 HTML/Firebase 구조에서는 React Query를 도입하지 않는다. 공용 상태 함수와 Firestore 구독 범위를 정리해 같은 목적을 달성한다.

## 11. MVP 재정의

### 1차 실사용 테스트

1. 로그인·역할 분리
2. 엑셀 이관 미리보기와 검증
3. 내 업무 행 입력·수정·완료
4. 담당자 이관과 가용성 경고
5. 프로젝트 상세의 전체 업무 목록

### 2차 조율 기능

1. 프로젝트 현황 집계
2. 팀 현황·인력 현황
3. 날짜 × 직군 일정 조율표
4. 마일스톤 영향 미리보기와 선후행 경고

### 3차 운영 기능

1. 사용자 관리·퇴사 재배정
2. 실행 취소와 변경 이력
3. 모바일 조율 화면
